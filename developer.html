ATTARIX — case study

An offline-first point-of-sale and retail ERP for small shops in Egypt, designed and built by me as a solo developer. Development used an AI coding assistant (Claude Code) as a pair programmer, working under my architecture, written invariants, review and test-first rules. Security is described at a high level only.

1. Summary

ATTARIX is a Windows desktop point-of-sale and back-office system for small and mid-size Egyptian retailers — grocery, clothing, mobile phones and electronics, spice shops (عطارة), auto parts, cafés and wholesalers. It runs the whole shop on one PC with no internet: sales and returns, shifts and cash drawers, purchasing and suppliers, stock by weight, by pack and by serial number, customer credit and cheques, double-entry accounting, payroll and attendance, and Egyptian e-invoice data. Shops that grow can pair several PCs on their local network, and an optional AI layer (using the shop's own provider key) reads supplier invoices and answers questions about the shop. The interface is Arabic, right to left.

2. System overview

ATTARIX is a Tauri 2 application: a Rust core process and a WebView2 window running a React + TypeScript interface. The design rule is that the webview is not trusted with the data: it holds no database permission at all. Every read and write is a call into Rust, which owns the SQLite file.

Layers, from the inside out:

  1. Domain core (src/core, src/hr/core) — pure TypeScript: no React, no I/O (invariant 16). Money arithmetic, invoice totals, refund allocation, the weighted-average stock value, payroll, the hybrid logical clock and the sync merge all live here and are unit-tested in isolation.
  2. Repositories (src/lib/repos) — every state-changing command writes its rows and appends its event in one SQLite transaction (invariant 6). Repositories also hold the business refusals (a serial product sold without its serial, a deactivated product on a purchase, a cash sale with no open shift).
  3. Rust core (src-tauri/src) — owns the database (two connections: a reader opened read-only, and one writer), decides the licence and edition gates, takes and verifies backups, runs migrations, serves sync, and proxies the AI and update requests.
  4. Screens — React components that read their own data from URL parameters (invariant 13) and never hold cross-route state.

3. The rules the system is built on

The project is governed by 19 written invariants. The ones that shape everything else:

  • Money is an integer number of piastres — never a float, never REAL (invariant 1). Every amount typed on a screen is parsed as text into piastres; more than two decimals is refused, never rounded.
  • Quantities are integer thousandths of their unit since 3.0 (invariant 19, migration 065): 1 piece = 1000, 0.250 kg = 250.
  • History is append-only. Ledger entries, stock movements, events and settings history cannot be updated or deleted — SQLite triggers refuse it (invariant 2). A correction is a counter-entry, never an edit.
  • Balances are computed, not stored. A customer's balance and a product's stock are derived from movements (invariant 4).
  • Policies are stamped. A sale line records the cost and the serial policy in force when it was sold; history never re-reads today's settings (invariant 10).
  • External input is validated at the boundary with zod — including every reply from Rust and every reply from an AI model (invariant 15).

4. Core flows

4a. A sale — from cart to journal

  1. Pricing. A line goes in at the customer's standard price for its level (retail or wholesale) and its unit (piece or pack). The customer's last price is offered, never silently applied. A pack line carries the pack's price so a carton of 12 at 100.00 is exactly 100.00, not 12 × 8.33.
  2. Totals. Line discounts, an invoice discount and VAT are folded once, in integer piastres (core/invoiceTotals.ts).
  3. Stock. Each line writes a stock movement. Its cost is stamped from the product's stored stock value — a proportional share, with the last pieces on the shelf taking whatever value is left so an empty shelf holds exactly zero.
  4. Serials. A serial-tracked product (phones, cameras) cannot be sold without naming each device, enforced in the repository, not the UI. Each device leaves stock at its own purchase cost and carries its warranty date.
  5. Cash. Every cash payment is bound to the open shift of the counted drawer; change handed back is never booked as drawer money. Card, wallet and bank tenders go to their own accounts and never touch the drawer count.
  6. Journal. The posting engine (repos/posting.ts) turns documents into double-entry entries, incrementally and append-only: each document owns an entry keyed by its source and signed by a hash of its lines — unchanged documents are skipped, changed ones are reversed and re-posted, vanished ones reversed. Every run is one transaction with a balance guard before commit.

A design decision worth naming: an earlier version balanced the books by plugging any difference into owner's capital — which meant every posting bug vanished into equity. It was replaced by an alarm: the pre-journal history is frozen once as a dated cut-over entry, each legitimate opening balance is its own entry, and any remaining difference between a control account and its live balance is reported to the owner, never booked.

4b. Returns — partial, by device, by weight

The rule (core/refund.ts) is that a customer gets back exactly what he paid for the units coming back. Because rounding is cumulative, a weighed line can be refunded in any number of partial weights and the last refund always lands the total to the piastre. A refund is its own document with its own date, so the month of the original sale is never rewritten. Purchase returns follow the same shape on the supplier side.

4c. Inventory valuation

  • Each product carries a stored stock value, and every movement moves it by exactly what the books post to inventory. The average cost is that value divided by the quantity — re-derived after inflows, never after a sale: under the weighted-average method a sale does not change the average, and deriving it from a sale made the converged cost depend on which PC made the sale (found by the multi-PC convergence tests).
  • Buying into negative stock (selling before the goods arrived) values the shelf at the purchase's real net cost and books the difference as a dated cost settlement — never into equity.
  • Serial units are valued individually: each device enters at its own net cost and leaves at it.
  • A read-only cost-check command replays a shop's purchases to report any product whose stored average drifted from the one its purchases imply — reported, never silently repaired.

4d. Payroll and the local-day rule

  • The month boundary. A payroll run is for one calendar month whatever day it is created on: a run made on the 1st for the previous month counts only that month's days, takes in nobody hired after it, and does not recover an advance paid on the 1st.
  • The local-day rule. Timestamps are stored as UTC instants, but a shop's day is local: a sale at 00:30 in Cairo is stored as the previous evening in UTC. Every "today", every report day, every journal date and every payroll month is derived from the local calendar day through one module (core/monthKey.ts), and a guard test refuses the UTC pattern in screens. Existing shops' journal entries were re-dated once, at start-up, behind a verified snapshot; an attempt that is refused or fails keeps nothing and is retried at the next start.
  • HR is isolated. The HR module (src/hr) reaches the rest of the app through one host file, enforced by a boundary test; and salaries never leave the main PC when sync is on.

4e. Multi-PC sync

Sync is a hub-and-spoke event log on the shop's LAN: one main PC (the hub) and the shop's other PCs (devices). Each device sells fully offline; nothing ever flows device-to-device.

Why it converges. Every node applies the same log in one total order — hub-stamped hybrid logical clock, then origin device, then origin sequence (sync/merge.ts). The domain folds are not commutative (a weighted-average cost is different if a sale falls between two purchases), so convergence comes from a shared order, never from the folds being reorderable. A replay from the genesis snapshot reproduces the same semantic state, which the tests check (trial balance, live documents, party balances, stock, unit statuses).

Key mechanisms:

Concern Mechanism
Duplicate delivery (normal on any network) An event's identity is (origin device, origin sequence); an applied-events ledger makes re-delivery a no-op. This is the only safe defence for additive folds (balances, stock, average cost) that a second application would silently double.
Id collisions between PCs Each PC mints document ids in its own numeric range (device index × 10⁹), with a durable per-table watermark that survives restore and wipe — so invoice:{id} keys stay stable everywhere.
An event that cannot apply Quarantine: it rolls back whole and is held with a reason; later events of the same origin wait behind it; other origins carry on; every drain retries. Never skipped silently, never guessed.
Master data edited on two PCs Last writer wins per entity, in canonical order, with the whole attribute set. Prices are stamped on sale lines, so a price edit never rewrites a sale.
The same serial sold on two PCs offline Both sales stand (real money from two customers); the conflict is listed for the owner, who resolves it on a dedicated screen.
Users, roles and shop settings Authored on the main PC only; a device applies them only if they come from the main PC it joined. No password hash travels in an event.
The journal Never synced — each node re-derives it from the same ordered log.
Salaries HR events never leave the main PC.
Joining A device joins from a verified genesis snapshot of the main PC (taken with every shift closed) plus every event since.
Mixed versions An event from a PC that has not yet taken the quantity migration is held with a plain-language reason until it upgrades — nothing is lost.
Switching it on Three locks must all be open: a build flag, the edition, and the shop's own switch. Anything unreadable counts as closed.

The Rust server is deliberately a dumb pipe: it authenticates the peer and stages bytes; all domain logic stays in the tested TypeScript core.

4f. Migrations — rehearsed, fail-closed

Migrations run in Rust before the webview exists, so no UI flag can stand between a pending migration and the data. Every migration follows a fixed order before it is registered: a rehearsal on a copy of a real database (every table's row count before = after, quick_check clean, no foreign key broken), then a test that proves the halt for that version, and only then registration. A parity test checks that the Rust migrator writes exactly the same migration records the previous plugin wrote, version by version.

Migration 065 — integer thousandths. Quantities moved from REAL to whole thousandths in 15 columns of 11 tables, rewritten in place in one transaction. Append-only tables are rewritten through a maintenance gate that their triggers honour only inside that transaction. The application reads and writes units at the database boundary: a stored quantity is converted by column name (core/quantityScale.ts), so domain code never sees thousandths, and SQL that multiplies a quantity by money divides by 1000 itself. The rehearsal lists any value that was not a whole thousandth before a shop upgrades.

4g. The AI assistant — provider-agnostic, human-approved

  • Features: supplier invoice → purchase lines; expense receipt → expense form; product from a photo; "ask your shop" questions; a daily summary draft; a polite debt-reminder draft. Smart alerts (unusual discounts or refunds by a cashier, stock about to run out) are computed by the program itself — no AI call — so they never depend on a key.
  • "Ask your shop" in two steps: the model first picks one of twelve allow-listed, read-only report functions (validated before anything runs); the program runs it; the model then sees only the resulting numbers and writes the answer. It never sees raw rows and cannot run arbitrary queries.
  • Bring your own key keeps the shop's data contract with its own provider, keeps the cost visible (each call shows its measured cost), and keeps the product working fully offline when no key is set.

4h. The release pipeline

  • The guard refuses rather than warns. Before a build: the version must be bumped consistently past the last release; the build date that seeds new trials must be fresh (and not in the future); no development key and no database file may be in the bundle; the tree must be clean and its commit already on the remote; migration parity must pass; and an internal comparison log of the licence logic must show recent, disagreement-free runs. After the build: the bundle is scanned again, and the guard tags the exact commit the build came from, annotating the tag with the installer's size and SHA-256 — so any installer a shop holds can be traced to its source.
  • A build that was abandoned must be recorded as superseded; a version number names exactly one installer.
  • Auto-update downloads over HTTPS, checks size and SHA-256 against a manifest signed with an asymmetric key and verified in Rust, accepts installers only from allow-listed hosts, installs only with no open shift and the admin's confirmation, and takes a backup first. Nothing is silent.

5. Security, at a high level

  • The webview cannot touch the database directly. All SQL goes through Rust: reads on a connection that is read-only by construction, writes on one gated writer.
  • The writer refuses schema changes from the interface with a SQLite authorizer (no CREATE, DROP, ALTER, ATTACH or setting pragmas), so database triggers that protect history cannot be removed from the UI side.
  • Licensing and edition gates are decided in Rust, offline, from signed activation codes; the UI's own checks are only the friendly first refusal.
  • Secrets live in the operating system's credential store, never in the database or in backups. Backups to a second location can be encrypted with a passphrase using an established format (age).
  • Multi-PC links use mutually authenticated TLS 1.3 with certificates exchanged at pairing; an IP address is used to find a peer, never to trust it (invariant 17); a device may push only its own events.
  • Identity is never taken from a request: guards resolve the acting user's rights from the database, including for the last-admin rule and for restores.
  • The embedded browser is hardened against being opened for remote debugging, and every release re-tests this on the installed binary.

6. Engineering decisions and trade-offs

Decision Why Cost accepted
Offline-first, local SQLite Egyptian shops lose internet often; a till that stops when the line drops loses sales. A local file also keeps native guarantees (fail-closed backups before migrations, hardware-bound licensing). Multi-PC needs a real sync design instead of one central database.
An event log for sync, not row replication Commands become facts with an actor, a device and a shift; replaying them in one order reproduces the same books on every PC, including order-sensitive folds like the weighted-average cost. The journal is re-derived per node. Every write path had to become an event with a tested replay, migrated one command family at a time behind a convergence test.
Integer piastres and integer thousandths Floating-point money and weights drift; integers make every total, refund and valuation exact and comparable to the piastre. A one-time migration of every quantity column and a strict boundary convention.
Numeric id ranges per device, not ULIDs Keeps integer ids, so document keys and line hashes stay valid across PCs without re-signing history. A durable allocator with watermarks that survive restore and wipe.
Bring-your-own AI key No server to run, no shared bill, the shop chooses its provider (Gemini included), and the product never depends on AI. Each shop must create a key; every reply must be parsed defensively.
Rust owns the data A compromised or misbehaving webview cannot rewrite history. Every database feature crosses IPC; performance was measured (the three heaviest reads got faster, not slower).
Report, don't plug An accounting system that silently balances itself hides its own bugs. Gaps are visible to the owner and must be explained.

7. Testing strategy

  • Red first. Every bug fix starts with a failing test that reproduces it; the fix is accepted only after the failure has been shown. Many tests are named after the defect they pin.
  • Pure core, heavy unit coverage. Domain functions have no I/O, so money, refunds, payroll, pricing, the HLC and the merge are tested directly.
  • Real SQLite in tests. Repository tests run against a real database with every migration applied, including the append-only triggers.
  • Standing invariants as assertions. Every money test ends by checking that the books show no unexplained posting gap; a full "ordinary day" test walks partial payments, split tenders, credit, partial refunds and returns and checks the books after every step.
  • Convergence tests for sync: two devices and a hub over an in-memory transport, then over real HTTP on loopback — full distribution, store-and-forward, idempotent re-delivery, total order, and replay-from-genesis equality.
  • Screen tests drive the real React screens end to end (dialogs, refusals, Arabic wording).
  • Rust tests cover the database gate, the authorizer, the fail-closed migration halt for each version, backup and restore ordering, the licence decision, TLS pinning and pairing.
  • Static gates: a strict lint configuration (no any, no float parsing of money, no index keys, no floating promises, a pure core) runs in a pre-commit hook; a binary guard refuses committed binaries.
  • Numbers: 596 test files; 3,702 TypeScript tests in the latest full run with 0 failures; 364 Rust tests.
